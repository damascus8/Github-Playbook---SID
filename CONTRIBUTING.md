# Contributing

Thanks for helping make this Playbook clearer and more useful.

## Before opening an issue or pull request

- Search existing issues and discussions first.
- Keep guidance practical for beginners and usable without paid tools.
- Link official documentation for claims about GitHub feature availability or limits.
- State whether a recommendation is required, recommended, or optional.
- Avoid presenting one language, framework, or company workflow as universal.

## Pull-request expectations

1. Explain the problem and the change.
2. Keep each pull request focused where possible.
3. Update the relevant guide, template, and README index together when needed.
4. Test YAML and workflow examples when practical; identify examples that require project-specific adaptation.
5. Search for stale placeholders, broken relative links, contradictory instructions, and unlabelled paid features.
6. Do not include real credentials, customer information, or private repository contents.

## Style

- Use plain English and short sections.
- Prefer checklists and concrete commands over vague advice.
- Explain acronyms at first use.
- Use `MUST` only for a baseline rule, `SHOULD` for a strong recommendation, and `MAY` for an optional choice.
- Every copied template must identify what a user needs to edit.

## Scope

This project provides engineering guidance and examples, not legal advice or a guarantee that a repository is secure or compliant. Pull requests should not promise otherwise.
